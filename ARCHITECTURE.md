# NIRNAY — Architecture

## Overview

NIRNAY is a single-page application (SPA) with no backend. All computation happens in the browser. Data is persisted to LocalStorage. There are no external API calls or server dependencies.

---

## Data Flow

```
User Input (Wizard)
    │
    ▼
DecisionInput { alternatives, criteria, weights, constraints, values }
    │
    ├─► filterFeasibility()        ← constraints.ts
    │       Returns: alternativeId → violations[]
    │
    ├─► normalizeAll()             ← normalization.ts
    │       Returns: alternativeId → criterionId → 0–100
    │       (only over feasible alternatives)
    │
    ├─► weighted scoring           ← decisionEngine.ts
    │       contribution[c] = normalizedScore[c] × (weight[c] / 100)
    │       totalScore = Σ contribution[c]
    │
    ├─► ranking + tie detection    ← decisionEngine.ts
    │       Sorted descending; scores within 0.01 = tie
    │
    ├─► tradeOff analysis          ← decisionEngine.ts
    │       Criteria where winner differs from runner-up by >5 normalized points
    │
    └─► generateExplanation()      ← explanationEngine.ts
            Returns: explanation string + criterion-level breakdown strings

DecisionResult → saved to LocalStorage → rendered on Results page
```

## Module Responsibilities

| Module | Responsibility |
|---|---|
| `types/decision.ts` | All TypeScript interfaces and types |
| `lib/decisionEngine.ts` | Orchestrates the full pipeline; also exports `runWhatIf` |
| `lib/normalization.ts` | Min-max normalization; exports `normalizeValue`, `normalizeAll`, `buildNormalizationContexts` |
| `lib/constraints.ts` | Hard constraint filtering and violation messages |
| `lib/explanationEngine.ts` | Auto-generates plain-English explanations from numbers |
| `lib/sensitivity.ts` | Runs engine over 16 weight values (5%–80%) for one criterion |
| `lib/storage.ts` | CRUD operations on LocalStorage (`nirnay_decisions`) |
| `lib/draftStore.ts` | In-progress wizard state in SessionStorage |
| `lib/export.ts` | JSON (full object), CSV (all score columns), print-ready HTML report |
| `data/demo.ts` | Static demo data (Food Delivery Decision) |
| `components/` | Reusable UI primitives (Card, Button, Badge, Alert, etc.) |
| `pages/` | Page-level components connected to React Router |

## State Management

NIRNAY uses React local state only (no Redux, no Zustand). State is:

- **Ephemeral** (wizard step data) — lives in `NewDecision.tsx` and `EditDecision.tsx` component state
- **Draft persistence** — `EditDecision.tsx` saves to SessionStorage on every change via `draftStore.ts`. Draft is loaded on mount, so browser navigation does not lose work.
- **Persisted** (saved decisions) — stored in LocalStorage via `lib/storage.ts` as `SavedDecision[]`

The Results, WhatIf, and Sensitivity pages load from LocalStorage on mount and are **stateless** with respect to saved data.

**What-If sandbox**: The WhatIf page does not mutate the saved decision. It runs `runWhatIf()` in memory. Clicking "Apply Scenario & Save" is the only way to persist the scenario result.

```
/decision/:id/sensitivity  Sensitivity Analysis
/history                   Decision History
/how                       How It Works

```

All routes are client-side (React Router v7). No server-side routing needed.

## Decision Engine: Key Design Decisions

1. **Pure function**: `runDecisionEngine(input: DecisionInput): DecisionResult` — no side effects, no state, no randomness.
2. **Normalization over feasible set only**: Infeasible alternatives are excluded before normalizing. This ensures the winner is chosen from a fair comparison of valid options only.
3. **Tie tolerance**: Scores within 0.01 are considered tied to avoid floating-point false positives.
4. **Trade-off threshold**: Criteria where normalized score differs by >5 points between winner and runner-up are listed as advantages/disadvantages.
5. **No LLM**: Explanations are generated by `explanationEngine.ts` using string templates filled with actual computed values.
6. **Deterministic**: Same inputs → same outputs always. There is no randomness, caching, or memoization that could affect results.

## Results Page Sections

In rendering order:

1. Recommendation card (or TieCard / NoFeasibleCard)
2. Edit actions strip (Change Priorities, Change Constraints, Review Evaluation, Edit Decision)
3. Explanation (auto-generated text + criterion contributions)
4. How This Score Was Calculated (collapsible formula + per-criterion table)
5. Ranking table (feasible sorted by rank, infeasible at bottom)
6. Weighted Score Ranking chart (stacked bar, Recharts)
7. Criterion-Level Comparison heatmap (horizontal bar, Recharts) — only when ≥2 feasible alternatives
8. Criterion Breakdown table (sorted by contribution descending)
9. Trade-off Analysis (winner vs. each runner-up)
10. Key Strengths & Weaknesses (criteria ≥70 = strength, <40 = weakness)
